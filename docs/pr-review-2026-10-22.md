## Repairs applied during integration

- **PTZ readback:** #170 passed a temporary copy of the V4L2 control structure to
  each read ioctl, then returned the untouched original. Current values and
  ranges therefore read as zero. The code now returns the kernel-written buffer;
  regression tests exercise nonzero responses and error propagation. Live tilt
  readback is now `7200`, matching `v4l2-ctl`.
- **Control ranges:** removed invented fallback ranges that masked ioctl errors.
  The GUI only shows controls with usable reported ranges, clamps zoom input,
  and uses 3600-unit pan/tilt slider steps matching this Tiny 2. Manual pan/tilt
  disables AI tracking so tracking does not fight the requested movement.
- **Preset storage:** #170 wrote beside the executable, which normally fails in
  `/usr/bin`. The shared GUI/CLI store now uses
  `$XDG_CONFIG_HOME/tiny4linux/custom_presets.json`, falling back to
  `~/.config/tiny4linux/custom_presets.json`. Saves replace the file by rename;
  save/delete reject corrupt existing JSON instead of overwriting it. Existing
  experimental preset files must be copied to the new location manually.
- **Preset state:** the GUI saves values queried through the camera interface,
  rather than its own old slider state. V4L2 pan/tilt reads can still be cached;
  they are not a physical position sensor after AI or manual gimbal movement.
- **GUI failures:** camera control and preset I/O errors are displayed rather
  than panicking. Status and PTZ values refresh after control operations and on
  periodic polls. This improves #76 but does not implement its entire busy-state,
  command-queue, and asynchronous completion design.
- **Other error paths:** oversized debug commands are rejected before buffer
  copying; exposure setting failures propagate; CLI preset errors exit nonzero;
  invalid preset numbers are checked before subtraction; `version` and shell
  completions work with the camera unplugged.
- **Compatibility:** preserved `Camera::new(&str)` and model-specific dispatch
  when reconciling the two camera PRs. Detection prefers Tiny 2, then Tiny 3,
  then Tiny 4K. Tiny 3 currently uses the Tiny 2 protocol path.

## Relevant issue reports: cause and remedy

### General controls and stale state

[#155](https://github.com/OpenFoxes/Tiny4Linux/issues/155) and
[#86](https://github.com/OpenFoxes/Tiny4Linux/issues/86) explain that general image
and PTZ controls use V4L2, while tracking and other vendor features use OBSBOT
commands. This fork integrates PTZ through #170; image controls remain available
through tools such as `v4l2-ctl` or the maintainer-linked Camset.

[#76](https://github.com/OpenFoxes/Tiny4Linux/issues/76) documents the GUI updating
its expected state before confirming the camera's actual state. A rejected or
unfinished command can leave misleading buttons. Error handling and polling are
improved here; the camera may still need time to finish moving or waking. Avoid
rapid conflicting operations while diagnosing this behavior.

### Disconnects, checksums and presets

[#171](https://github.com/OpenFoxes/Tiny4Linux/issues/171) contains measurements
from a **Tiny 2 Lite, firmware 6.2.5.3**, including disconnects when streaming starts
soon after USB enumeration or after rapid streaming restarts mixed with extension
unit writes. This is a contributor report, not a demonstrated diagnosis for this
Tiny 2. If disconnects occur, try waiting about a minute after reconnecting USB and
using one sustained video stream during control testing instead of rapid restart
cycles. No firmware change is claimed here.

The same issue derives CRC-16/USB framing and documents hardware preset operations
and the selector-based preset-name cursor. Empty-store status `0x03` must not be
parsed as an entry. It also reports status byte offsets differing from assumptions
in this project. These are useful protocol leads, but they were not applied to
Tiny 2 from Lite measurements without validation. Local file presets from #170
are a separate mechanism, not implementation of #171's hardware preset protocol.

### Model and kernel differences

[#72](https://github.com/OpenFoxes/Tiny4Linux/issues/72) and
[#108](https://github.com/OpenFoxes/Tiny4Linux/issues/108) concern detection and
model differences. Tiny 4K is an older camera with a different command protocol;
#169 supplies a separate implementation. Its author tested a Tiny 4K, not a Tiny 2.
It is useful compatibility work, not evidence of a Tiny 2 USB fix.

[#154](https://github.com/OpenFoxes/Tiny4Linux/issues/154) reports incorrect
negative pan/tilt speed limits on kernel 6.18. This machine reports driver/kernel
7.0.12; the issue alone does not establish that the same bug affects it. This
integration uses absolute pan/tilt rather than continuous speed controls.

[#27](https://github.com/OpenFoxes/Tiny4Linux/issues/27) tracks gesture settings;
full gesture configuration remains incomplete. [#52](https://github.com/OpenFoxes/Tiny4Linux/issues/52)
was a historical GUI packaging path bug and is closed. [#97](https://github.com/OpenFoxes/Tiny4Linux/issues/97)
was a GitHub deployment/token problem, not a camera failure.

## Read-only checks on the connected Tiny 2

Host enumeration found the physical Tiny 2 on `/dev/video2` and `/dev/video3`,
plus a separate OBSBOT virtual camera on `/dev/video42`. Detection selected the
physical camera. These checks did not start a stream, move the gimbal, change
settings, or perform sleep/wake cycles.

| Check                            | Observed result                                                      |
| -------------------------------- | -------------------------------------------------------------------- |
| Compiled CLI `info`              | Exit 0; sleeping, static tracking, standard speed, HDR enabled       |
| `pan`                            | `0`, range `-468000..468000`                                         |
| `tilt`                           | `7200`, range `-324000..324000`                                      |
| `zoom`                           | `0`, range `0..100`                                                  |
| Compare against `v4l2-ctl --all` | PTZ values and ranges agree                                          |
| Current stream format            | 1920×1080 MJPG, 15 FPS configured; not a measurement of achieved FPS |
| White balance                    | Automatic white balance off, temperature 2000 K                      |

If the general problem is a colour cast, inspect the manual 2000 K white-balance
setting. If it is low frame rate, inspect the 15 FPS stream configuration in the
application consuming video. Neither setting was changed. The camera was asleep
at the status check; that is an observation, not proof of why an earlier failure
occurred.
